3 ОПИС ВИКОНАНОЇ РОБОТИ
	3.1. Розробка бізнес логіки серверної частини програмної системи
	У процесі розробки серверної частини системи SmartFood було розроблено повний цикл бізнес-логіки обробки замовлення - від створення клієнтом до завершення виконання персоналом. Основною метою бізнес-логіки є забезпечення коректної взаємодії між ролями користувачів, даними бази та правилами роботи ресторану.
	Клієнтська частина взаємодії реалізована без обов’язкової авторизації, оскільки ідентифікація здійснюється за номером столу. Клієнт має доступ лише до меню та можливості сформувати замовлення. Після створення замовлення система автоматично присвоює йому статус created. Подальший життєвий цикл замовлення контролюється персоналом закладу. У бізнес-логіці визначено такі ключові стани:
* cooking - кухар прийняв замовлення в роботу;
* ready - страва приготована та готова до доставки;
* delivered - офіціант доставив замовлення клієнту;
* paid - фінальне підтвердження оплати.
	Перехід між статусами можливий лише для відповідних ролей, що контролюється через механізм JWT-авторизації та рольових перевірок.
	Після встановлення статусу delivered продаж фіксується у статистиці та враховується під час формування популярності страв.


	3.2 Розробка функцій адміністрування серверної частини програмної системи
	Адміністрування у системі SmartFood доступне лише авторизованим користувачам з роллю адміністратора. Кожна адміністративна дія проходить обов’язкову перевірку JWT-токена та підтвердження ролі. Основні функції адміністрування включають:
* Керування користувачами: створення нових облікових записів, встановлення та зміна ролей (клієнт, офіціант, кухар, адміністратор). Для захисту даних паролі зберігаються у БД у вигляді хешів (bcrypt).
* Керування меню (CRUD): адміністратор може створювати, редагувати й видаляти страви, змінювати опис, ціну та категорію.
* Моніторинг замовлень: адміністратор може переглядати всі замовлення, їх статуси, час створення, суму, відповідальних співробітників.
* Аналітика та статистика продажів: реалізовано можливість отримання інформації про найпопулярніші страви.
* Управління системою ролей: адміністратор має окремий API-ендпоінт для зміни ролі будь-якого користувача.
	3.3 UML-діаграми діяльності та взаємодії
	Діаграма діяльності демонструє послідовність кроків у процесі створення та виконання замовлення - від перегляду меню клієнтом до завершення доставки офіціантом. У цій діаграмі відображено ключові рішення, ролі користувачів, переходи між статусами та залежності між діями. Вона описує бізнес-процес і підтверджує коректність розробленої логіки життєвого циклу замовлення. Також її можна переглянути за посиланням.

Рисунок 3.1 - UML-діаграма діяльності
	Діаграма взаємодії була побудована для моделювання обміну повідомленнями між користувачем, API та базою даних під час оновлення статусу замовлення та виконання операцій персоналом. У ній відображено, як система перевіряє JWT-токен, визначає роль користувача, звертається до бізнес-логіки, оновлює дані в базі та повертає результат. Така діаграма дає змогу простежити технічну взаємодію між компонентами системи, підтверджує цілісність архітектури та узгодженість бізнес-правил із серверною реалізацією.  3  import json

 5  def role_required(*roles):
 6      def decorator(func):
 7          def wrapper(*args, **kwargs):
 8              identity = json.loads(get_jwt_identity())
 9              if identity is None or identity["role"] not in roles:
10                  return jsonify({"error": "Доступ заборонено"}), 403
11              return func(*args, **kwargs)
12          wrapper.__name__ = func.__name__
13          return wrapper
14      return decorator
