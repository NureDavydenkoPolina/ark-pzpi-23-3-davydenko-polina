3 ОПИС ВИКОНАНОЇ РОБОТИ
	3.1 Розгортання програмної системи SmartFood та налаштування середовища
	У межах лабораторної роботи було виконано розгортання програмної системи SmartFood з акцентом на відтворюваний запуск серверної частини та перевірку взаємодії з базою даних і IoT-клієнтами. Для розгортання серверної частини було використано Docker (Docker Compose), що дозволило стандартизувати середовище виконання застосунку та спростити запуск на іншому комп’ютері без ручного встановлення всіх залежностей.
	Серверна частина SmartFood (Flask + SQLAlchemy + JWT + Swagger/Flasgger) була зібрана у Docker-образ і запущена як контейнер з пробросом порту 5000 на хостову систему. Важливим налаштуванням було забезпечення доступності застосунку ззовні контейнера: Flask було запущено у режимі прослуховування на всіх адресах (0.0.0.0), завдяки чому API стало доступним у браузері за адресою http://127.0.0.1:5000. Таким чином, після запуску контейнера стало можливим відкривати ендпоінти системи та здійснювати тестові запити.
	База даних MS SQL Server використовувалася як уже наявна та попередньо налаштована (без розгортання у контейнері). Підключення бекенду до БД виконувалося з контейнера через мережевий міст Docker за допомогою адресації host.docker.internal та порту 1433. Було використано SQL-автентифікацію через окремого користувача БД (smartfood_user). Рядок підключення було винесено у змінну середовища SQLALCHEMY_DATABASE_URI, що дало змогу запускати застосунок у різних середовищах без зміни коду. Додатково було налаштовано параметри безпечного підключення драйвера (ODBC Driver 18), зокрема вимкнення примусового шифрування для локального стенду та довіру до сертифіката, що дозволило уникнути помилок TLS при локальному розгортанні.
	IoT-частина системи розгорталася як окремі клієнтські скрипти (без контейнеризації). Для IoT-клієнтів було налаштовано конфігураційний файл config.json, де вказуються базова адреса бекенду, ідентифікатор столика, облікові дані для авторизації та інтервал опитування. Після цього IoT-клієнти запускалися у локальному середовищі та зверталися до бекенду через HTTP, використовуючи REST API.

	3.2 Перевірка стабільності, коректності роботи компонентів та налаштування параметрів
	Після розгортання системи було проведено перевірку працездатності та взаємодії всіх компонентів: серверної частини, API, бази даних та IoT-клієнтів. Перевірка починалася з контролю того, що бекенд-контейнер коректно стартує та приймає запити з хостової системи. Далі виконувалася функціональна перевірка REST API через виклик ключових ендпоінтів системи. Було підтверджено, що бекенд відповідає на запити, повертає дані у форматі JSON та коректно обробляє параметри запитів.
	Окрему увагу було приділено перевірці підключення до бази даних, оскільки саме цей етап найчастіше спричиняє проблеми при розгортанні. Під час тестування було виявлено, що контейнеризований бекенд має мати мережевий доступ до SQL Server; для цього налаштовувалися мережеві параметри SQL Server (TCP/IP), відкривався потрібний порт та перевірялася доступність підключення. Після налаштування мережі було підтверджено, що бекенд успішно встановлює з’єднання з БД і може виконувати операції читання та запису. Коректність роботи бізнес-логіки перевірялася через типові сценарії: отримання меню, створення замовлення для столика, додавання позицій до замовлення, перегляд складу замовлення, а також розрахунок підсумкової вартості. Додатково було перевірено, що дані зберігаються у відповідних таблицях, а зміни у замовленні відображаються у подальших запитах.
	Перевірка IoT-частини виконувалася шляхом запуску двох клієнтів. Table IoT перевіряв можливість отримання меню та створення/оновлення активного замовлення для заданого table_id. Kitchen IoT виконував авторизацію у системі, періодично опитував бекенд із заданим інтервалом та відображав нові або оновлені замовлення. Такий підхід дозволив підтвердити стабільність роботи системи в режимі повторних запитів (polling) і коректність взаємодії клієнтів із серверною частиною в реальному часі. 

	3.3 Демонстрація функціональності SmartFood відповідно до Vision & Scope (розділ 2.2)
	Функція MF-1 Перегляд меню онлайн - у поточній реалізації демонструвалася через виклик ендпоінта отримання меню. Система повертала перелік страв, доступних у меню, у форматі JSON. Меню містить основні атрибути страви (назва, ціна, опис), що відповідає вимогам перегляду меню клієнтом. Також через адміністративні методи можна змінювати перелік страв і одразу бачити оновлення у результатах запиту, що підтверджує актуальність даних у меню.
	Функція MF-2 Формування замовлення - була продемонстрована на сценарії створення замовлення для конкретного столика і додавання позицій. Система дозволяє створити замовлення, після чого клієнт додає обрані страви із зазначенням кількості. Після додавання позицій замовлення можна переглянути у розширеному вигляді з переліком страв та підсумковою сумою. Для редагування кошика передбачено зміну кількості (через повторне додавання позиції, що збільшує кількість) і видалення позицій із замовлення. Таким чином, логіка кошика/замовлення реалізована на сервері й може використовуватися клієнтом.
	Функція MF-3 Надсилання замовлення на кухню - демонструвалася через взаємодію Table IoT та Kitchen IoT. Після формування замовлення на стороні клієнта воно стає доступним для кухні як активне замовлення у системі. Кухонний клієнт з заданим інтервалом виконує опитування сервера та виводить нові замовлення або зміни у складі/сумі замовлення. Таким чином підтверджено, що після створення замовлення дані стають доступними для кухні, а сервер виконує роль центрального вузла, що передає інформацію між клієнтами.
	Функція MF-4 Відстеження статусу замовлення - демонструвалася через зміну статусу замовлення на сервері та подальше отримання актуального стану. Замовлення має визначені стани (створено, готується, готово, доставлено), а серверна логіка обмежує переходи між станами залежно від ролі користувача (офіціант/кухня). Клієнт може отримати поточний статус через API та відобразити його, що дозволяє забезпечити відстеження етапів виконання замовлення у реальному часі.
	Функція MF-5 Виклик офіціанта у поточному прототипі може бути продемонстрована як точка розширення системи: у Table IoT інтерфейсі передбачена дія Call waiter, яка імітує сценарій виклику персоналу.
	Функція MF-6 Оплата замовлення - також була представлена у вигляді бізнес-вимоги та області для подальшого розвитку. У поточній реалізації демонструється можливість переходу замовлення до відповідного стану (paid) та збереження результату в базі даних. 
	Функція MF-7 Адміністративна панель - демонструвалася через адміністративні ендпоінти. Адміністратор може керувати меню: додавати нові страви, змінювати їх параметри та видаляти позиції. Також демонструвалася можливість перегляду списку користувачів, управління ролями та отримання статистики (наприклад, популярність страв на основі замовлень). Окрім цього, адміністратор може переглядати активні замовлення, що дозволяє контролювати поточне навантаження та стан системи.
	Функція MF-8 Управління столами реалізована у базовому вигляді через прив’язку замовлення до table_id. При створенні замовлення система зберігає номер столика, а також підтримує запит на отримання активного замовлення для конкретного столу. Це дозволяє персоналу і клієнтам працювати зі своїм замовленням та забезпечує коректну прив’язку в межах залу. 
	Функція MF-9 Система сповіщень - продемонстрована у вигляді автоматичних повідомлень, що реалізуються через механізм опитування (polling). Kitchen IoT отримує повідомлення про нові або оновлені замовлення, що фактично є аналогом сповіщень для кухні. Така реалізація є працездатною для прототипу та може бути замінена або доповнена більш сучасними механізмами (WebSocket, push-повідомлення) без зміни загальної логіки системи.
	Функція MF-10 Збір аналітики - підтверджується через збереження історії замовлень і позицій у базі даних та можливість отримувати агреговані дані через адміністративні запити. Оскільки в БД накопичуються записи про замовлення, позиції, кількість та суму, адміністрація може аналізувати продажі, популярність страв і загальну активність. 
	3.4 Як розгорнути SmartFood 
	Щоб запустити SmartFood на комп’ютері, потрібно, щоб працювали дві речі: база даних (MS SQL Server) і серверна частина (Backend). 
	Спочатку перевіряємо, що MS SQL Server запущений і база SmartFood існує. Далі важливо, щоб SQL Server дозволяв підключення по мережі: має бути увімкнений TCP/IP і відкритий порт (частіше за все 1433). 
	Після налаштування достатньо виконати команду docker compose up --build. Якщо все налаштовано правильно, контейнер стартує і бекенд буде доступний у браузері. Далі можна перевірити, що API працює: наприклад, відкрити ендпоінт меню http://127.0.0.1:5000/api/menu і побачити JSON-відповідь.
	Коли сервер працює, запускаються IoT-клієнти. IoT-клієнт столик дозволяє формувати замовлення, а кухня - бачить нові замовлення та їх оновлення. 

4 ВИСНОВКИ
	У ход було розгорнуто програмну систему SmartFood у локальному стенді з використанням Docker/Docker Compose для серверної частини. Контейнеризація дозволила швидко відтворювати середовище запуску, ізолювати залежності бекенду та стандартизувати процес розгортання незалежно від налаштуванань ОС на хості. 
	Перевірка функціональності підтвердила, що система коректно обробляє запити API та забезпечує взаємодію між компонентами: сервером, БД і клієнтами. У результаті отримано працездатний стенд для демонстрації, який можна розширювати далі: додавати повноцінний веб/мобільний інтерфейс, розширювати адміністративні сценарії, а також покращувати механізм сповіщень без зміни загальної архітектури.
